## Approved v1.2 Increment — Optional Uploads and Disk Preflight

- **Copy option:** extend the existing `wp-devkit/bin/wp-devkit-copy.sh` with `--uploads include|exclude`. Preserve the current include behavior when the option is absent for backward compatibility, but make the mode an explicit question in the agent workflow. Both baseline and candidate must use the **same** selected mode. No new copy engine, dependency, or installer.
- **Exclude semantics:** when excluding, skip only the contents of `wp-content/uploads/` (including nested media), leaving a writable, initially empty uploads directory in **each** copy. Copy all other necessary site files as before and preserve source ownership/permissions without modifying the original. Database snapshots and attachment records are unchanged. No symlinks, shared mutable uploads or source mounts.
- **Disk preflight:** before the first copy, estimate source site size and uploads separately, project the file space for two sibling copies for both modes, and inspect destination filesystem free space. Recheck before the second copy where needed. Refuse an obviously insufficient destination before writing; warn when exact availability cannot be determined. This is an estimate, not a guarantee: SQL snapshots, two database volumes, image layers, and cache can need additional space or live on another filesystem. No capacity planner or synchronization.
- **Skill and manual workflow:** update `wp-devkit/skills/wp-devkit/SKILL.md`, the short prompt, README and reporting example. During discovery show sizes and candidate destination, then **ask** whether to copy uploads before execution. The same mode must be configurable manually with the flag. Document that when excluded, WordPress media attachment records remain but files are absent, so broken images/media tests may be expected and are not automatically classified as upgrade regressions. Include selected mode and disk-limit assumptions in the report.
- **Validation:** cover include/exclude, nested uploads, an empty writable uploads directory, identical options in both copies, no source mutation, capacity refusal before a copy starts, and an approximate disk estimate for two siblings. Keep existing safety and acceptance suites green. This is the only newly approved functional feature.

## Fixed Invariants

- Use `wp-devkit/` within the actual WordPress root and independent sibling directories (`project-x-baseline/`, `project-x-candidate/`) for test copies, each with its own DevKit, Compose project, network, and DB volume. The only optional file omission is the **contents** of uploads, consistently excluded from both copies; leave writable uploads directories and report the choice. No shared mutable files, worktrees, or symlinks. Copy operations must not recursively include prior tests or overwrite existing destinations.
- Before a copy's first startup, its database configuration points to its own internal database. Identical test credentials are acceptable in separate networks.
- Before copying, assess filesystem space for both sibling file trees; refuse clearly insufficient capacity without creating a partial copy and document estimates/limitations. Independently import one consistent logical snapshot into two databases. Temporary SQL snapshots remain outside every HTTP-served WordPress root, including the source, baseline, and candidate roots. Do not transfer physical data directories between database versions.
- Normal startup and changing the PHP image do not silently update existing core. Updating WordPress is a separate, explicit action.
- Change one candidate comparison dimension at a time where practical. Report unavoidable additional differences.
- Do not perform global pruning, use fixed global container names, or mutate the original or live environment. Before cleanup, validate actual Compose resource ownership rather than trusting a matching name in editable files. Reject target identity/name conflicts.
- Do not add mandatory interceptors, secret scanning, cron disabling, external HTTP blocking, or environment-type changes. Docker isolation does not guarantee prevention of external outbound actions.
- Do not introduce dependencies on Git, GNU Make, a specific AI product, Compose overrides, personal paths/integrations, or agent frameworks. README procedures must work without the distributed Agent Skill; no mandatory agent registration. Do not lock, synchronize, or automatically coordinate changes to the original.

## Expected Implementation Result

This folder includes all runtime files, the standalone public README, portable `START_HERE.md` and `skills/wp-devkit/SKILL.md`, the adapted AI prompt, and an example compact Markdown report. Root development documentation and AI tooling remain tracked in Git but are excluded using `.gitattributes` `export-ignore`. The skill directs agents to the same Compose, WP-CLI, and project commands available to manual users, without a complex new CLI. Real GitHub ZIP acceptance remains pending publication.

The report states the goal and selected comparison dimension, baseline/candidate parameters, uploads mode, approximate disk-space estimate, initial snapshot, actual before/after versions and resolution of latest, commands/exit codes, PASS/FAIL/SKIPPED/NOT CONFIGURED/ERROR, differences, omitted-media limitations, and cleanup state. A successful PHP 8.4/MariaDB pilot does not qualify PHP 7.4 or remove/defer configurable MySQL.
